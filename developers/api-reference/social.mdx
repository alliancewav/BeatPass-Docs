Use these endpoints for follows, reposts, and a user's library. Public profile reads and authenticated personal actions have different permissions; approval does not grant access to private profiles or another user's preferences.

<Info>
  **Base URL:** `https://open.beatpass.ca/api/v1`

  **Authentication:** Write operations require a valid Bearer token. Read operations on public profiles use optional auth.
</Info>

---

## User Following

### Follow User

### Unfollow User


Read the authenticated account's followed-users list and compare user IDs. Keep the displayed state in sync after a successful follow or unfollow.


### Get User's Followers

```http
GET /api/v1/users/{user}/followers
```

### Get User's Followed Users

```http
GET /api/v1/users/{user}/followed-users
```

## Follow Limits

Shared API throttles apply; this reference does not specify a separate account-following quota. Repeating a user follow or unfollow is successful and leaves the existing state unchanged; a self-follow is ignored. Artist follow is also idempotent, but unfollowing an artist not currently followed returns `409`.

## Reposts

### Toggle Repost

Toggle repost status for a track or album. If already reposted, it removes the repost.

```http
POST /api/v1/reposts/toggle
```

<ParamField body="repostable_type" type="string" required>
  Use `track` for a track or `album` for an album.
</ParamField>

<ParamField body="repostable_id" type="integer" required>
  ID of the existing track or album to repost or un-repost.
</ParamField>

### Get User's Reposts

```http
GET /api/v1/users/{user}/reposts
```

### Repost Limits

Shared API throttles apply. No separate repost quota is specified here. A successful response returns `action: added` or `action: removed`. Because this is a toggle, blindly retrying can undo the first request.

## User Library

### Add to Library

Add tracks, albums, or artists to the authenticated user's library.

```http
POST /api/v1/users/me/add-to-library
```

<ParamField body="likeables" type="array">
  Send an array of items to target. Each item needs `likeable_id` and `likeable_type`.
</ParamField>

<ParamField body="likeables[].likeable_id" type="integer" required>
  ID of the item to add.
</ParamField>

<ParamField body="likeables[].likeable_type" type="string" required>
  Item type: `track`, `album`, or `artist`.
</ParamField>

### Remove from Library

Remove tracks, albums, or artists from the user's library.

```http
POST /api/v1/users/me/remove-from-library
```

<ParamField body="likeables" type="array">
  Send an array of items to target. Each item needs `likeable_id` and `likeable_type`.
</ParamField>

<ParamField body="likeables[].likeable_id" type="integer" required>
  ID of the item to remove.
</ParamField>

<ParamField body="likeables[].likeable_type" type="string" required>
  Item type: `track`, `album`, or `artist`.
</ParamField>

### Get Liked Tracks

```http
GET /api/v1/users/{user}/liked-tracks
```

### Get Liked Albums

```http
GET /api/v1/users/{user}/liked-albums
```

### Get Liked Artists

```http
GET /api/v1/users/{user}/liked-artists
```

### Library Limits

Use endpoint pagination and returned validation errors for library and playlist limits. This reference does not specify fixed saved-item or playlist-size ceilings. Library writes do not document universal retry idempotency.

## Notification Preferences

Manage notification delivery channels for the authenticated user. Available notification types have independent channel selections. Use the returned `available_channels` and subscription definitions; channel availability does not guarantee delivery on every device.

<Note>
  Use `me` for the authenticated user route, or pass the authenticated user's numeric ID. The backend resolves both forms.
</Note>

### Channel Keys

- `email` — Email notifications
- `in_app` — Notification center storage and live activity in open tabs
- `mobile` — FCM-backed push for registered, supported devices with permission to receive notifications

### Get Notification Subscriptions

Retrieve the authenticated user's notification configuration, available channels, saved selections, and role-based context.

```http
GET /api/v1/notifications/me/subscriptions
```

**Response:**

```json
{
  "status": "success",
  "available_channels": ["email", "in_app", "mobile"],
  "subscriptions": [
    {
      "group_name": "Messages",
      "subscriptions": [
        {
          "name": "Direct Messages",
          "notif_id": "new_message",
          "description": "When you receive a direct message"
        }
      ]
    }
  ],
  "user_selections": [
    {
      "notif_id": "new_message",
      "channels": {
        "email": true,
        "in_app": true,
        "mobile": true
      }
    }
  ],
  "user_context": {
    "is_artist": true,
    "is_verified_artist": false
  }
}
```

### Update Notification Subscriptions

Update one or more notification channel preferences.

```http
PUT /api/v1/notifications/me/subscriptions
```

<ParamField body="selections" type="array" required>
  Array of notification preference updates.
</ParamField>

<ParamField body="selections[].notif_id" type="string" required>
  Notification identifier to update, such as `new_message`.
</ParamField>

<ParamField body="selections[].channels" type="object" required>
  Channel state object keyed by `email`, `in_app`, and/or `mobile`.
</ParamField>

**Response:**

```json
{
  "status": "success"
}
```

<Note>
  Use the exact backend channel keys in update payloads: `email`, `in_app`, and `mobile`. The legacy `browser` key is no longer part of the notification settings contract.
</Note>

## FCM Device Tokens

Register and manage Firebase Cloud Messaging device tokens for the authenticated user. The API stores tokens only; obtaining the token is the responsibility of the client app through the Firebase SDK.

### Register or Refresh FCM Token

Store or refresh an FCM token for the authenticated user.

```http
POST /api/v1/fcm-tokens
```

<ParamField body="token" type="string" required>
  FCM registration token returned by the Firebase client SDK. Maximum 500 characters.
</ParamField>

<ParamField body="platform" type="string">
  Device platform. Supported values: `web`, `android`, `ios`. Defaults to `web`.
</ParamField>

<ParamField body="device_name" type="string">
  Optional device label, typically the user agent or app/device name. Maximum 200 characters.
</ParamField>

**Response:**

```json
{
  "status": "ok"
}
```

<Note>
  Register a token only for a device used by the authenticated account. These FCM token endpoints return `{ "status": "ok" }`, while the notification subscription endpoints above use the standard `{ "status": "success" }` response envelope.
</Note>

### Delete FCM Token

Remove an FCM token for the authenticated user, for example during logout.

```http
DELETE /api/v1/fcm-tokens
```

<ParamField body="token" type="string" required>
  FCM registration token to remove.
</ParamField>

**Response:**

```json
{
  "status": "ok"
}
```

<Note>
  This endpoint currently expects the FCM token in a JSON request body. Some HTTP clients or intermediaries strip bodies from `DELETE` requests, so use a client path that preserves the JSON payload. Keeping the token out of the URL also avoids encoding and length issues with long FCM tokens.
</Note>
