Read the HTTP status first, then the endpoint's payload. These notes cover verified common cases; they are not an exhaustive list of every provider, proxy, or framework error.

## Error Response Format

There is no universal error envelope. Framework validation can return `message` and `errors`; some endpoints add `success: false` or a string `error`. Commerce endpoints can use `status`. Never require fields that the specific endpoint does not document.

Illustrative validation response:

```json
{
  "message": "Validation failed",
  "errors": {
    "field_name": ["A value needs correction."]
  }
}
```

Use explicit fields such as `error_code` or `reason_code` only where documented. Human-readable messages can change or be translated.

## HTTP Status Codes

| Status | How to handle it |
| --- | --- |
| `400` | Check the request and the operation's current state |
| `401` | Check authentication before sending another protected request |
| `403` | Stop and check account, endpoint, and resource permission |
| `404` | Check the identifier and whether the resource is available to this account |
| `409` | Refresh the relevant state; some operations require renewed acceptance |
| `422` | Correct the indicated fields or eligibility problem |
| `429` | Read the message and headers; distinguish HTTP throttling from an exhausted feature allowance |
| `5xx` | Preserve the request context and check the operation's state before retrying a write |

## Authentication Errors

Missing, invalid, or expired tokens normally produce `401` on protected routes. An authenticated account can still receive `403` because it lacks API approval, endpoint permission, verified email where required, or access to the resource.

Create or revoke developer tokens in **Account Settings → Developers**. Tokens expire after 90 days. A fresh token does not bypass account restrictions. See [Authentication](/developers/auth).

## Track & Upload Errors

`POST /tracks` validates required metadata and licensing declarations before saving. A normal new-track payload includes `name`, `image`, `duration`, `artists`, `licensing_type`, `key`, `scale`, `bpm`, `url`, and `src` for your completed authorized audio upload; additional fields depend on the offer, samples, and AI disclosure. Read the `422` field errors rather than using one generic upload-error message.

An acoustic duplicate detected during creation can return `409`, with `is_duplicate`, `original_track`, and `similarity_score`. Stop and review the result instead of repeatedly uploading the same audio.

File limits, publication readiness, and processing failures are separate from track creation. Do not assume every file failure returns `422`, that every processing timeout returns `504`, or that deleting a track makes all subsequent reads return `410`. A successful save does not certify processing completion or rights clearance.

## Purchase & Licensing Errors

### Purchase Flow

These cases apply to price calculation and purchase initiation:

| Condition | Status | Recovery |
| --- | --- | --- |
| Purchases disabled | `403` | Stop checkout |
| Offer, price, currency, payout setup, ownership, or account role is ineligible | `422` | Read the message and current purchase status |
| Required legal identity or signed producer offer is missing | `422` | Complete the indicated identity or authorization step |
| Explicit buyer acceptance or quote hash is invalid | `422` | Review the displayed quote and submit valid acceptance |
| Accepted rights, price, fee, total, or currency changed | `409` | Fetch a fresh quote, display it, and obtain acceptance again |

Producer accounts cannot start new exclusive catalog purchases. Existing purchases and valid licenses are separate from eligibility to start a new purchase. Purchase status includes `can_purchase`, `can_start_checkout`, `requires_legal_name`, and an optional `reason_code`; a human-readable `reason` is not a stable error code.

### Payment Errors

Stripe.js payment confirmation and BeatPass API calls are different response surfaces. Do not convert every card decline into an assumed BeatPass `402` response. Show the safe error returned by the payment flow, then inspect purchase status before initiating another payment. Never log a client secret, card data, or a full payment payload.

### License Errors

| Operation and condition | Status | What to inspect |
| --- | --- | --- |
| Public UUID verification: malformed UUID or missing record | `404` | `valid: false` and `message` |
| Public verification: record found | `200` | `valid`, `status`, `integrity_verified`, and replacement fields when present |
| PDF-data retrieval: no active license | `404` | Returned message |
| Certificate retrieval: current certificate is invalid or incomplete | `409` | Identity or certificate recovery guidance |

A successful HTTP verification response is not itself proof of an active license. Original grants, replacement certificates, identity completion, expiration, revocation, and integrity are separate states. A certificate-view problem does not erase the original grant.

## Beat Request Errors

Creation uses `422` for invalid fields or duration, `409` when a posting UUID is reused with changed details, and `429` for insufficient tokens or an exhausted posting allowance. A matching retry with the same posting UUID and unchanged payload returns the existing request without another debit. A token shortage is not fixed by repeating the request after a short HTTP backoff.

Submission can return:

- `403` for missing upload permission or lack of ownership/collaboration.
- `422` for an invalid track, non-hosted audio, duplicate submission, or the five-submission per-producer limit.
- `409` with `error: duplicate_audio` when duplicate audio is detected.
- `400` for submitting to your own request.
- `404` for a missing request; the endpoint can also use this when the request is no longer available.
- `410` with `error: request_expired` when the fulfillment service identifies an expired request.

Renewal requires ownership and a request within its renewal window. An active request or expired renewal window returns `400`; an insufficient token balance returns `429`. See [Beat Requests](/developers/api-reference/beat-requests) for the current renewal behavior.

## Producer Program Request Errors

Backstage request creation uses explicit conflict codes:

| `error_code` | Status | Recovery |
| --- | --- | --- |
| `backstage_request_pending` | `409` | Wait for the existing application decision |
| `backstage_request_revoked` | `409` | Direct the applicant to `/contact` for an appeal |

These guards apply across request types. If both histories exist, `pending` takes precedence. Missing creation permission returns `403`; API approval does not grant that permission.

## Audio Recon Errors

Track match retrieval requires sign-in and access as the direct track owner, a linked credited producer. Missing authentication returns `401`, denied access `403`, and a missing track `404`.

If no credited artist is verified, the response can be successful with an empty `placements` array and `artist_verified: false`. A verified collaborator can meet this eligibility requirement; it is not limited to the primary artist. An empty result is not evidence of infringement clearance.

## Messaging Errors

Message text is required and limited to 2,000 characters. Start-conversation validation also checks recipient IDs and group size. Missing both recipient fields returns `400`; invalid values, self-conversations, and groups without two other participants return `422`.

The sender must follow recipients. A paused conversation or an unmet follow requirement returns a validation error. Membership checks apply to conversation reads and mutations; there is no documented universal blocked-user error contract.

For supported sends, use the same `client_message_id` UUID and unchanged payload to reconcile a retry. Reusing that UUID for different content returns a validation error. See [Messaging](/developers/api-reference/messaging).

## Collection & Library Errors

Do not assume fixed library, playlist, or editor ceilings that the endpoint has not documented. Use its validation response.

Adding tracks already present in a playlist succeeds and reports `added_count` and `duplicate_count`. For collaborative invitation failures, read the returned status and message before retrying.

## Social & Following Errors

Repeating a user follow or unfollow succeeds without creating another relationship. Repeating an artist follow also succeeds; unfollowing an artist that is not followed returns `409`.

Reposting is a toggle. A successful response returns `action: added` or `action: removed`; repeating a request can undo it. Do not treat it as an idempotent create, or expect a universal `409 Already reposted` response.

## Radio Errors

Use the documented seed type and identifier, then handle the returned status and payload. This reference does not establish separate skip-limit or concurrent-stream error codes.

## Rate Limiting

HTTP throttling normally provides its wait in the `Retry-After` header. A `retry_after` JSON field is not guaranteed. Illustrative headers only:

```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 300
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1700000060
Retry-After: 60
```

Pause the affected request budget, respect the returned wait, and use bounded retries for safe reads. See [Rate Limits](/developers/rate-limits) for a GET-only retry example.

## Server Errors (5xx)

A server error does not tell you whether a write completed. Before repeating a purchase, upload, message, or other mutation, read the available state and use only that endpoint's documented retry or reconciliation mechanism.

`503` can indicate maintenance or an unavailable scheduled snapshot; it does not always mean the whole platform is down. Check the [status page](https://status.beatpass.ca) when a service-wide issue is suspected.

For persistent failures, contact [support@beatpass.ca](mailto:support@beatpass.ca) with the endpoint, method, approximate time and timezone, status, and a sanitized error. Exclude tokens, client secrets, personal records, and bank details.

## Troubleshooting Checklist

<Steps>
  <Step title="Read the status and payload">
    Use `message`, field errors, or documented machine codes when present. Preserve enough sanitized context to diagnose the issue.
  </Step>
  <Step title="Check access and current state">
    Verify the account, permissions, resource, feature allowance, and latest quote or purchase state.
  </Step>
  <Step title="Choose the recovery step">
    Correct validation fields, request the needed permission, wait for a rate-limit window, or reconcile an uncertain write. Retry only when safe.
  </Step>
  <Step title="Ask for help if needed">
    Send the sanitized context to support when the documented recovery does not resolve the issue.
  </Step>
</Steps>
